## 一、UZI-Skill 如何解决 22 维度的噪音问题

UZI-Skill 不是简单平均 22 维得分。它用了一套**四层降噪机制**：

### 第一层：深度分级（lite/medium/deep）

用户自行选择分析深度，决定了噪音控制强度：

| 模式 | 维度数 | 评委数 | 噪音处理 |
|------|--------|--------|---------|
| lite 速判 | 核心 7 维 | 10 位代表 | 用最重要维度，省掉不必要的信息 |
| medium 标准 | 全 22 维 | 66 位完整 | 中等深度 |
| deep 机构级 | 22 + 强化 fallback | 66 + Bull-Bear 辩论 | Playwright 兜底 10 维，多空辩论对抗噪音 |

**启示**：我们在 Dashboard 上也可以设"精简/标准/深度"三档。

### 第二层：数据缺口显式标注（不强填默认值）

```
缺失数据≠默认值 — 缺失就标 data_gap，不假装有数据
低覆盖率→红色 low-confidence banner，不假装可信
```

我们的 `src/governance/data_gaps.py` 已经这样做了 — 这是个优势。

### 第三层：13 条机械自检 Gate（物理阻断）

`lib/self_review.py` 在报告生成前跑 13 条自动检查：

| 级别 | 检查 | 作用 |
|------|------|------|
| critical | 行业碰撞检测 | 防逻辑矛盾 |
| critical | 维度缺失/空数据/占位符 | 防静默失败 |
| critical | panel 全 skip | 防无人评审 |
| critical | agent 未审查 | 防 Agent 偷懒 |
| warning | DCF 全 0 | 覆盖率警告 |

**关键**：critical 问题会**物理阻止**报告生成，逼迫走过数据缺口补救流程。这跟我们的 Quality Gate + Publish Gate 思路完全一致。

### 第四层：规则引擎 242 条量化条件（不是平均打分）

最核心的一点：UZI-Skill 不是"每个维度各打 1-10 分然后取平均"。它用 **242 条量化规则** 做条件打分：

```
巴菲特看到 PE=33 → 规则 #A-3：PE>25 → 直接看空（不依赖其他维度加权）
赵老哥分析美股 → 规则 #F-12：A股游资不看美股 → skip（不出分）
段永平看到好生意 + 差价格 → 规则 #E-5：好生意优先 → override 看多
```

每条规则有**具体触发条件**，不是模糊的"感觉这个维度应该得 7 分"。

**我们的差距**：我们的 8 个角色评分是 LLM prompt-based，虽然也能给出具体判断和理由，但没有 UZI-Skill 那种"242 条规则精确触发"的机械感。不过这也有优劣——LLM 的推理能力更强，规则引擎的确定性更高。

## 四、UZI-Skill 核心差异化优势总结

### 1. 规则引擎确定性 > LLM 模糊性

UZI 的 242 条量化规则在 Python 中硬编码，具有确定性：同样的输入永远产生同样的输出。我们的 LLM prompt 更适合开放推理，但有随机性。

### 2. 数据采集并发化

v3.0 的 Pipeline 架构支持 22 个 Fetcher 并发采集。我们的爬虫还是串行的 — 这是我们最大的性能差距。

### 3. 评委三层评估体系

```
真实持仓 → 行业亲和度 → 量化规则
先看仓位（真金白银），再看能力圈（会不会看），最后用规则打分
```

我们的角色没有"真实持仓"和"行业亲和度"这两个前置过滤层，直接进入分析。这是最值得借鉴的设计。

### 4. 三档深度配置

用户可以根据时间预算选 lite/medium/deep。我们目前只有一档。

### 5. 13 条机械自检 Gate

跟我们的 Quality Gate 思路一模一样，但 UZI 实现得更极端 — critical 物理阻止报告生成。

| 优先级 | 借鉴内容 | 接入方式 |
